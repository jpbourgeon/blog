# editorial-publish

Perform only mechanical publication operations for an identified article and target mode: `draft`, `unlisted`, `public`, or an approved `revision` promotion to `public`. No invocation implicitly grants editorial authority.

1. Read `AGENTS.md`, the actual Docusaurus configuration, deployment workflow, current article files and their French/English counterparts. Resolve the actual default locale and file layout; do not guess project setup, URLs, branch triggers, deployment behavior, or existing publication state. Stop any unsupported deployment operation rather than inventing infrastructure.
2. Bind one canonical article, its paired locales, requested target mode, and the exact FR/EN candidates being authorized. Read `.42p/editorial-reviews/<canonical-article-slug>.md` when present. For any public publication or revision promotion require `result: PASS`, matching `candidates.fr/en` paths and normalized content SHA-256 digests, `targets.fr/en` paths and projected canonical digests, and matching applicable standards/Capture Git blob SHAs. For a revision, require that both current canonical files match `baseline.fr/en.git_blob_sha` and that their effective canonical routes remain stable. Use the **same deterministic normalizer and projection** as `editorial-verify`, excluding only top-level `draft` and `unlisted` fields from hash normalization; `slug` is significant. Do not attempt public publication with a missing, stale, uncommitted or unverifiable report. Confirm that the report was committed prior to the proposed publication/promotion commit so an independent gate can reconstruct its parent state.
3. Apply native Docusaurus frontmatter consistently to both locales, and require explicit author permission when withdrawing or exposing an existing public article:
   - `draft`: set `draft: true` and remove `unlisted`; excluded from the production site (though source Markdown may remain public in a public Git repository). Author approval for public exposure is not needed.
   - `unlisted`: remove `draft` (or set false) and set `unlisted: true`. This creates a publicly accessible, URL-discoverable preview, **not access control**. Require explicit authorization to expose this candidate for preview; it is not final public approval. For a revision, expose only the separate temporary article and leave canonical files unchanged. Report any review defects or limits, without claiming a final verification pass is required merely to preview.
   - `public`: remove both `draft` and `unlisted` (or set false). Require the matching overall `PASS` editorial review and explicit human approval of those exact FR/EN candidates **and** their projected public exposure. For a revision, use the dedicated promotion operation rather than simply changing the temporary article's visibility. Neither silence, a previous article approval, nor an agent report supplies permission. Approval is an explicit author decision at publication time, not an extra frontmatter status or approval database.
4. For a public `revision` promotion, perform only the predetermined `P(candidate, baseline)` transformation specified in `AGENTS.md`: replace the canonical FR/EN files with their projected outputs and delete both temporary FR/EN candidate files in **one atomic Git commit**. Preserve canonical paths and effective URLs. Copy all other candidate metadata and body **exactly as verified**; only visibility and canonical-slug transformations are mechanical. If an unverified change to date, identity, link, asset or any other content would be necessary, return to `editorial-write` then `editorial-verify`. Confirm the final normalized canonical SHA-256 hashes equal `targets.fr/en.content_sha256`, and that the old baseline blobs matched the report before the commit. For ordinary visibility changes, change only `draft`/`unlisted` and confirm candidate hashes remain stable. Never resolve editorial questions or rewrite prose while publishing. If the normalizer, projection or report cannot be checked reliably, fail closed for public publication.
5. Commit the paired changes together and use only the configured, authorized GitHub Pages workflow. Before exposing new or revised canonical content, require an **independently executed deterministic gateway** that checks the report, current target hashes, relevant Git blob revisions and, for revision promotions, the parent commit's candidate and baseline blobs and the deletion of both temporary files. Reject a mismatched locale, missing report, stale baseline, stale references, unexpected canonical edit, nonmechanical transformation or unguarded deployment path. A successful agent-side check does not replace CI; require build, route/link and temporary-search-index checks when installed. Unlisted previews may be authorized without a final `PASS`; they must never overwrite the canonical public article. If the real gateway or deployment path is missing, prepare only permissible changes and report the blocker without implying publication.
6. Check resulting file paths, metadata, both localized routes, and absence of temporary articles after promotion. Verify the site build and search-index exclusions when the site is installed. Report separately: verified report identity, files committed, branch/PR status, CI status, deployed mode and accessible URLs **only if observed**. Human permission given in conversation is not independently proven by the content-integrity gate. Never claim a site is live merely because a commit or workflow succeeded.

Use Git history for the audit trail. Do not introduce an editorial edition number, a new publication database, approval token, or custom preview system. Revising a published article follows the same Capture/reconciliation (when applicable) → write temporary pair → authorize unlisted preview (if wanted) → verify candidate and canonical projection → author decision → atomic promotion cycle.
