# editorial-publish

Perform only mechanical publication operations for an identified article and target mode: `draft`, `unlisted`, or `public`. No invocation implicitly grants editorial authority.

1. Read `AGENTS.md`, the actual Docusaurus configuration, deployment workflow, current article files and their French/English counterparts. Resolve the actual default locale and file layout; do not guess project setup, URLs, branch triggers, deployment behavior, or existing publication state. Stop any unsupported deployment operation rather than inventing infrastructure.
2. Bind one article, its paired locales, requested target mode, and the exact FR/EN candidates being authorized. Read `.42p/editorial-reviews/<article-slug>.md` when present. For public publication, require `result: PASS`, matching candidate paths and SHA-256 editorial-content digests for both locales, and matching applicable standards/Capture Git blob SHAs. Compute each digest using the same deterministic normalization as `editorial-verify`, excluding **only** top-level `draft` and `unlisted` frontmatter fields. Reject a missing/stale/unverifiable report, not just a different manual edition number (none is used). Git blob SHAs of complete article files may change solely because visibility fields changed; they are provenance, not this publication match.
3. Apply native Docusaurus frontmatter consistently to both locales:
   - `draft`: set `draft: true` and remove `unlisted`; excluded from the production site (though source Markdown may remain public in a public Git repository). Author approval for public exposure is not needed.
   - `unlisted`: remove `draft` (or set false) and set `unlisted: true`. This creates a publicly accessible, URL-discoverable preview, **not access control**. Require explicit authorization to expose this candidate for preview; it is not final public approval. Report any review defects or limits, without claiming a final verification pass is required merely to preview.
   - `public`: remove both `draft` and `unlisted` (or set false). Require the matching overall `PASS` editorial review and explicit human approval of those exact FR/EN candidates **and** their public exposure. Neither silence, a previous article approval, nor an agent report supplies permission. Approval is an explicit author decision at publication time, not an extra frontmatter status or approval database.
4. Do not make substantive edits, resolve editorial questions, or change wording during this operation. If authoring or verification becomes necessary, stop and delegate that distinct work. Preserve other frontmatter, rationale links, dates and identifiers; only change `draft`/`unlisted` for the authorized mode. Confirm the editorial-content digests are unchanged after the visibility edit. If the normalizer or report cannot be checked reliably, fail closed for public publication.
5. Commit the paired visibility changes together, then use only the repository's configured and authorized GitHub Pages workflow. Before public deployment, require an **independently executed deterministic gateway** (for example a CI check) that re-evaluates the review `PASS`, both current normalized digests and all recorded reference revisions; it must fail closed. The skill's own assertion of success does not count as a mechanical gate. Keep unapproved edits to already exposed content off an auto-deploying `main`. If that gateway, the real deployment path, or required permission is missing, prepare only permissible changes and report the blocker without implying publication.
6. Check that the resulting files have the intended metadata, the localized site can be built when tooling is available, and deployment/URLs can be verified when infrastructure permits. Report separately: files committed, branch/PR status, CI status, deployed mode and accessible URLs **only if observed**. Never claim a site is live merely because a commit or workflow succeeded.

Use Git history for the audit trail. Do not introduce an editorial edition number, a new publication database, approval token, or custom preview system. Revising a published article follows the same Capture/reconciliation (when applicable) → write → verify → author decision → publish cycle.
