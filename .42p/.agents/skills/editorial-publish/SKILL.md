# editorial-publish

Perform only mechanical publication operations for an identified article and target mode: `draft`, `unlisted`, `public`, or an approved `revision` promotion to `public`. No invocation implicitly grants editorial authority.

1. Read `AGENTS.md`, the actual Docusaurus configuration, deployment workflow, current article files and their French/English counterparts. Resolve the actual default locale and file layout; do not guess project setup, URLs, branch triggers, deployment behavior, or existing publication state. Stop any unsupported deployment operation rather than inventing infrastructure.
2. Bind the requested mode, canonical article, exact FR/EN candidate files and target paths. For a public transition, require a previously committed overall `PASS` report at `.42p/editorial-reviews/<canonical-article-slug>.md`, explicit author approval of the **exact** bilingual versions and their public exposure, and matching candidate `SHA256(N(candidate))`, projected target `SHA256(N(P(candidate, baseline)))`, applicable reference Git blob IDs and (for revisions) canonical baseline Git blob IDs. The same shared, tested `N`/`P` implementation must be used by `editorial-verify` and this skill; CI uses it for its independent checks. Exclude only top-level `draft`/`unlisted` from `N`; both temporary and canonical `slug` remain material. Check the original effective URLs and linked assets. Refuse missing, stale, uncommitted or unverifiable evidence; do not interpret the report as human authorization.
3. Apply native Docusaurus frontmatter consistently to both locales, and require explicit author permission when withdrawing or exposing an existing public article:
   - `draft`: set `draft: true` and remove `unlisted`; excluded from the production site (though source Markdown may remain public in a public Git repository). Author approval for public exposure is not needed.
   - `unlisted`: remove `draft` (or set false) and set `unlisted: true`. This creates a publicly accessible, URL-discoverable preview, **not access control**. Require explicit authorization to expose this candidate for preview; it is not final public approval. For a revision, expose only the separate temporary article and leave canonical files unchanged. Report any review defects or limits, without claiming a final verification pass is required merely to preview.
   - `public`: remove both `draft` and `unlisted` (or set false). Require the matching overall `PASS` editorial review and explicit human approval of those exact FR/EN candidates **and** their projected public exposure. For a revision, use the dedicated promotion operation rather than simply changing the temporary article's visibility. Neither silence, a previous article approval, nor an agent report supplies permission. Approval is an explicit author decision at publication time, not an extra frontmatter status or approval database.
4. For an approved revision, apply **only** `P(candidate, baseline)`: remove visibility fields, restore the existing canonical `slug` (or remove the preview-only slug if the original had none), and write the exact resulting FR/EN content at the original canonical paths. Delete both temporary candidate files in **one atomic Git commit** with both canonical updates. Compare both resulting normalized digests with the report's `targets.fr/en.content_sha256`. For ordinary publication, change only the native visibility fields in the paired files. Do not rewrite prose, dates, links, assets or other metadata; if any such correction or a changed canonical route is needed, return to writing and verification. The shared transformation must be tested on the actual frontmatter format; do not improvise a serializer in this skill.
5. Use only the configured GitHub Pages workflow. Before public exposure, require an **independent, fail-closed deployment gate** on the exact commit/artifact: verify the matching `PASS` report was committed and unchanged in its parent; compare final canonical FR/EN normalized digests with its expected targets; check applicable reference and prior canonical baseline Git blob IDs, paired promotion, required temporary-file deletions, permitted changed paths, route/build results and preview search-index exclusions. For a revision, CI must read **only** the two parent-commit candidate blobs to independently verify their identities and the minimal `P` transition; for a new article it checks the preceding draft/preview and its visibility-only transition. It must not reconstruct the full parent tree. Reject direct unverified edits to public articles, partial locale changes, unexpected editorial modifications and any deployment path that bypasses the gate. The deployment job must depend on successful checks; a successful agent-side check or Git commit is insufficient. The gate checks integrity, **not** human consent. If the real gate or deploy configuration is missing, do not claim that a public publication is protected or complete.
6. Check resulting file paths, metadata, both localized routes, and absence of temporary articles after promotion. Verify the site build and search-index exclusions when the site is installed. Report separately: verified report identity, files committed, branch/PR status, CI status, deployed mode and accessible URLs **only if observed**. Human permission given in conversation is not independently proven by the content-integrity gate. Never claim a site is live merely because a commit or workflow succeeded.

Use Git history for the audit trail. Do not introduce an editorial edition number, a new publication database, approval token, or custom preview system. Revising a published article follows the same Capture/reconciliation (when applicable) → write temporary pair → authorize unlisted preview (if wanted) → verify candidate and canonical projection → author decision → atomic promotion cycle.
